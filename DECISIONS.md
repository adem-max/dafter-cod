# Decisions

Every choice made while building this kit, with one line of reasoning.
Newest decisions are added at the bottom of each section.

## Platform

- **ERPNext v16 on Frappe v16** (built on 16.50.0 / 16.51.0, also tested on 16.51 / 16.52): v16 is the latest stable major (branch `version-16`, October 2026). `develop` is the future v17 and is not stable.
- **Python 3.14, Node 24, MariaDB 10.11, Redis 7**: Frappe v16 requires Python 3.14 and Node ≥ 24 and supports MariaDB 10.6 to 11.8. Ubuntu 24.04 ships MariaDB 10.11.
- **Ubuntu 24.04 LTS for the server guide**: that is what everything was tested on. Ubuntu 26.04 LTS should work but was not tested.
- **The GitHub repo is the Frappe app itself** (the `dz_cod` package sits at the root): `bench get-app https://github.com/adem-max/dafter-cod` works directly.
- **No core changes, everything in `dz_cod`** (or in dz_core for what every client needs): project rule. We use hooks, custom fields, a Workflow, Webhooks and a few small doctypes.
- **Runs on top of dz_core** (repo dafter-core, October 2026): `required_apps = ["erpnext", "dz_core"]`. dz_core is the base every client gets (setup wizard, sector template, tax regime, legal invoices, import workbook); this app adds only the online-sales part. `new_client.prepare` calls dz_core's prepare first, so the wizard and the tax step live in one place. Producers who sell by phone or wholesale get dz_core alone, without this app's Sales Order workflow.
- **Repos renamed dafter-cod and dafter-core, app names unchanged** (`dz_cod`, `dz_core`): renaming a Frappe app means renaming its Python package on every live site; the brand lives in the repo names. `bench get-app` still puts the code in `apps/dz_cod`.
- **Brand: Sijil (company), Daftar (the ERP)** (22 October 2026): Sijil is the umbrella brand for every SaaS, Daftar this ERP's product name, dz_cod its online-sales part. Reasons in dafter-core DECISIONS.md. Note only: nothing renamed yet.
- **IFU replaces "remove the default 19 % VAT"**: dz_core's tax regime does the same for IFU clients and keeps 19 % for régime réel clients.
- **Orders leave from dz_core's "Produits finis"** on new client sites, instead of a separate "Stock principal". The demo shop keeps its own warehouses.
- **Default warehouse on the Company, not Stock Settings**: ERPNext 16.51 moved it; writing Stock Settings `default_warehouse` did nothing there. Up to 16.50 the Company has no such field, so the demo loader writes whichever exists (19 October 2026: the 16.50 test bench failed on the Company-only version).
- **The split with dz_core is finished** (19 October 2026, dafter-core docs/SPLIT.md): the wilaya list (doctype DZ Wilaya), phone formatting, the Customer phone and wilaya fields, the backup scripts, the restore check and the server guide live in dz_core. This app keeps what only an online seller needs: the rate fields on each wilaya, commune and address on the Customer, the courier communes and offices (DZ Commune, DZ Stop Desk), and the feature switches.
- **Feature switches moved to dz_core** (19 October 2026, right after the split, where they had first been kept here): the hub became dz_hub and manages every client, most without this app, so the mechanism belongs to the base. This app declares its four features with `dz_features = ["dz_cod.features.FEATURES"]` and keeps the courier and webhook guards; `dz_cod.features` still exposes `is_enabled` & co. so COD modules did not change. `dz-cod-features` is an alias of dz_core's `dz-features`; the site_config key became `dz_features` (the old one is moved on migrate).

## Reference data

- **69 wilayas, not 58** (the list now lives in dz_core, `dz_core/setup/wilayas.py`; the zones and example rates stay here, `setup/wilayas.py`): law 26-06 of 4 April 2026 (JO n° 25) created 11 wilayas, and decree 26-206 (JO n° 40) set their numbers 59 to 69. I could not open the Journal officiel itself; numbers and names come from several Algerian press articles quoting the decree. **Double-check them.**
- **Each new wilaya remembers its parent wilaya**: couriers may keep the 58-wilaya codes for a while (the transfer runs until 31 December 2026).
- **Parent wilayas of 59–69 come from press reports**, not from the law text. **Double-check them.**
- **Communes are free text**, not a master list: the 1,541 communes would need a verified source; listed in LATER.md.
- **…until the courier's own list is imported**: for Yalidine clients, *Importer communes et bureaux Yalidine* fills **DZ Commune** with Yalidine's spellings, and the order's *Commune* becomes a pick list of the order's courier's communes (field type Autocomplete: free text while that list is empty, and for a courier without one, such as Manuel). Yalidine refuses names it does not know, so its list is the source that matters for shipping. The field type was switched from Data directly in the database (`switch_commune_to_autocomplete`): Frappe's Custom Field refuses Data → Autocomplete although both are the same varchar column.
- **Example shipping rates in 6 zones (400 DA Alger home delivery … 1,400 DA far south)**: placeholders. Replace them with each client's courier rate card.
- **Default courier cost = customer rate**: most small sellers pass the courier price straight to the customer; edit per wilaya if not.
- **Phone rule**: mobile = 05/06/07 + 8 digits, landline = 9 digits; `+213` and `00213` are converted to `0`. Unknown formats are kept as typed, never destroyed.

## New doctypes (rule 3: only when a standard one does not fit)

- **DZ Wilaya** (label "Wilaya", a dz_core doctype since October 2026; its rate fields are this app's custom fields): ERPNext has no list of Algerian provinces with rates. `Territory` was considered but it is ERPNext's sales-hierarchy tree; mixing addresses and courier rates into it would confuse sales targets and pricing rules.
- **COD Settings** (label "Paramètres COD", single record): rule 4 — per-client differences must live in settings, not code.
- **Courier Settlement + Courier Settlement Item** (label "Versement"): nothing standard matches "a third party's statement matched line by line against our orders". Payment Entry is per party (one customer); Bank Reconciliation works on bank lines, not parcels. The money itself is booked by one Journal Entry per Versement (COD accounting, below).
- **DZ Commune and DZ Stop Desk**: each courier's communes and offices, imported from the courier (Yalidine today). No standard doctype lists Algerian communes or courier offices; Address and Territory were rejected for the same reasons as for DZ Wilaya. Each record belongs to a connector and is named `<connector>-<courier's id>` (`Yalidine-1630`, since October 2026; before, Yalidine's bare id): a new import updates instead of duplicating, and a second courier's list (its own spellings, its own office ids) lives next to Yalidine's instead of overwriting it. The order's pick lists show its courier's list; the parcel sends the office's id at the courier (`center_id`), not our record name. Patches `rename_place_fields` and `name_places_by_connector` moved the older records.
- **Courier Webhook Event**: one line per event pushed by Yalidine, named by its event id, so a duplicate delivery is refused by the database itself. Frappe's Webhook Request Log only records webhooks we send, and Integration Request has no unique key on the event id. Cleared after 30 days (Log Settings).

## Order life cycle

- **The life cycle is a standard Frappe Workflow on Sales Order** ("Commande COD"): it gives buttons, roles, history comments and list colours for free.
- **Confirmer = submit the Sales Order**: before confirmation the operator must be able to edit everything (size, address) during the phone call; after it, stock is reserved and the order is locked.
- **Two cancel states**: "Annulée" (draft, customer said no on the phone) and "Annulée après confirmation" (submitted then cancelled). Frappe cannot cancel a draft, so one state cannot cover both.
- **Stock reservation = ERPNext's standard "reserved qty"** (soft reservation, automatic on submit), not Stock Reservation Entries (hard reservation): simpler and enough for a small shop. Hard reservation is in LATER.md.
- **Stock check at confirmation warns by default and can block** (setting): a print-on-demand seller confirms before printing.
- **Expédier moves the parcel to a "Chez transporteur" warehouse; Livrée makes the Delivery Note** (21 October 2026, SCF advice; until then the Delivery Note was made at Expédier). The sale, its TVA and its cost belong to the delivery to the buyer, and refusal rates in COD are high: a Delivery Note at shipment booked a cost of sales and reversed it for every refused parcel. The transfer posts nothing (inventory accounts per item), the warehouse shows what each courier holds, and the stock stays reserved on the main warehouse until delivery, so the confirmation check counts the parcels in transit back as available. The Delivery Note carries the lots the shipment moved, so the lot a buyer got is the lot that left. Courier and tracking number go to its standard "Transporter" and "Transport Receipt No" fields.
- **Retournée (before delivery) transfers the parcel from "Chez transporteur" to "Retours"**, with its lots, and closes the Sales Order so ERPNext never reserves that stock again. Nothing was sold, so there is nothing to reverse. An order shipped before 0.3.0 still has its Delivery Note and return note.
- **Inspection uses standard Stock Entries**: Material Transfer (Retours → main) for good pieces, Material Issue for damaged ones, linked back to the order with a custom field.
- **Invoiced at Livrée, booked at the Versement** (20 October 2026; until then no invoice was made, revenue stayed out of the general ledger and dz_core's sales reports missed online sales): see "COD accounting" below.
- **Delivery details are stored on the order** (phone, wilaya, commune, address), copied from the customer when empty: the courier needs a snapshot per order, and COD order entry must be fast. ERPNext's Address and Contact doctypes are not used for COD.
- **Unanswered calls are counted by the Workflow itself** (the "update field" option of the "Injoignable" state), with no code. The "Pas de réponse" button disappears at the maximum set in COD Settings (default 3).
- **Standard roles only**: Sales User confirms, Stock User prepares/ships/delivers/returns, Accounts User settles, Sales Manager may edit cancelled orders. "Allow self approval" is on because the shops are tiny teams.
- **A single-role user can move the orders of their own steps** (29 October 2026, review of 27 October, 1.2; decision D1 by Adem). Frappe saves the order on every step, and saving a submitted order wants write *and* submit on it, which ERPNext gives neither Stock User nor Accounts User: with the roles DEPLOY.md hands out, the first "Préparer" failed. `cod/permissions.py`:
  - Custom DocPerm gives both roles write and submit on Sales Order, and Stock User select on Account and read on Sales Invoice (what "Marquer livrée" needs to make the delivery note, the invoice and its payment), on every migrate. **Trade-off:** once Custom DocPerm exists for a doctype, ERPNext's later changes to its standard permissions no longer reach it (dz_core accepted the same for its delete locks).
  - A has_permission hook narrows them back: without a sales role, a user may write or submit only an order already submitted whose state, as saved, their role owns in the workflow; never a draft (Frappe's hooks can only narrow). A hook answers True to leave Frappe's answer: Frappe reads None as a refusal.
  - `check_change_after_submit` lets them change only the courier, tracking number and stop desk (and the workflow state): never ERPNext's own fields, the lines (ERPNext's "Update Items" included) or Daftar's other fields. Since 0.4.2 (review of 31 October 2026, C) **no user** may change Daftar's read-only fields on a submitted order (`dz_settlement`, `dz_payment_entry`, the dates...): "read only" only hides a field in the form, and through the API an Accounts User could point `dz_settlement` at another Versement and hide an unpaid parcel from the month's courier check. The code writes those fields with `db_set`, or in the order hooks that run after the check.
  - The invoice is mapped onto a target flagged ignore_permissions, and only ERPNext's payment *builder* runs as Administrator: the payment is inserted and submitted as the real user, so its owner and the audit trail name who marked the order delivered. Since 0.4.2 that step goes through `as_administrator()`: Frappe 16's `set_user` also replaces the session's id and data, the request's form_dict and cache, and switching back restored none of them, so a browser request saved an emptied session at its end (it recovered only through Frappe's fallback to the database copy).
- **The "Expédier" button opens a small dialog** (courier + tracking number) before the workflow action, because the tracking number must be saved before the move.
- **Event dates can be forced through `order.flags.dz_event_date`**: only the demo loader uses it, to replay 60 days of history with correct past dates.
- **Lots are ERPNext's to pick** (20 October 2026): for batch-tracked products (a food or cosmetics producer selling online), ERPNext 16 fills in one lot per line when a delivery note is saved, and refuses a line that one lot cannot cover. *Expédier* and the return inspection switch that off on their lines, so ERPNext's own outward bundle takes the lots oldest first, as many as needed; the delivery and a return then carry the lots the shipment moved. dz_core's demo engine keeps its own splitter: it backdates documents, and ERPNext skips expired lots by today's date.
- **Two channels on one site: COD and direct sale** (20 October 2026): a Frappe Workflow covers every Sales Order of a site, so a producer who also sells online had every wholesale order go through the COD checks, delivery fee and states. Each order now has a channel (*Canal*: COD or Vente directe), taken from the customer's usual channel, else COD Settings' default (COD). A direct sale skips this app's hooks and has its own short path in the same workflow, Nouvelle → *Valider* → **Validée**, then ERPNext's own delivery note and invoice; the COD buttons only show on COD orders (transition conditions). Validée is the first submitted state, so an order submitted by code lands there, not in Confirmée. Orders made before got COD (patch). The COD counters, charts and *Commandes par jour* count COD orders only.

## Courier connectors

- **Adapter pattern with three methods** (create shipment, get status, get tracking): the rest of the app never knows which courier is used.
- **"Manuel" is the default connector**: tracking typed by hand, status moved by hand.
- **"Mock" connector works offline**: tracking `MOCK-<order>`, statuses simulated in the Redis cache.
- **Yalidine connector built from a verbatim copy of its docs, without an account** (October 2026): the official docs sit behind the merchant login; a verbatim copy (API + webhooks, September 2026) in an open-source project was used, every endpoint and field comes from it, and points it leaves open are marked `UNVERIFIED` in the code. Tested only with a fake HTTP layer (`unittest.mock.patch` on `requests.request`) answering the docs' JSON examples. A real-parcel check with a client's keys is required before going live (checklist in docs/COURIER_INTEGRATION.md §4). ZR Express waits for ZR's official docs. Y8 (Versement from Yalidine payments) is not built.
- **`freeshipping: true` on Yalidine parcels**: our amount to collect already includes the delivery fee. Yalidine's docs define `false` as "paid by the receiver", so `false` risks the customer paying the fee twice; with `true` Yalidine deducts its fee from the payout, as our settlement expects. The plan said `false`; the first real parcel decides.
- **Only "Livré" and "Retourné au vendeur" move a Yalidine order**: "Retour vers vendeur", "Echèc livraison"... mean the parcel is coming back but not here, and Retournée moves stock into the Retours warehouse. Yalidine's exact words go into *Statut chez le transporteur* so the team sees them.
- **Statuses read from `parcels/?tracking=…` (50 per call)**, not `histories/`: one line per parcel with `last_status`, so no paging; the hourly sync asks each courier for all its parcels at once (`get_statuses`).
- **A parcel already created for the order is reused** (`GET parcels/?order_id=`): the API call happens inside the "Expédier" transaction, so a failure after it would otherwise create a second parcel on the next click.
- **Quota memory in Redis, shared by web and workers**: a quota window at 0 or a Retry-After is remembered per courier; a click gets a clear message, a background job waits (up to 60 s) and retries once. Repeated 429s can get the keys disabled, so we never hammer.
- **Yalidine prices import into the courier costs only**, one call per wilaya 1.5 s apart (40/min under the 50/min limit), price of the chef-lieu commune; customer prices stay the seller's decision. A 2026 wilaya Yalidine does not know gets its parent's cost.
- **Webhooks: store fast, apply in a job**: Yalidine wants a 2xx within 10 s and disables the webhook after 7 failed deliveries. The signature (HMAC-SHA256 of the raw body) is checked against the secret of every Yalidine courier; unsigned or wrongly signed bodies get a 400 and are not stored. An event older than the status already stored is ignored (Yalidine does not guarantee order). Webhooks move orders only when automatic sync is on, and the hourly sync stays as the safety net.
- **Wilayas 59–69 sent as their parent** to Yalidine, unless imported communes show Yalidine knows them: its docs list 58 wilayas.
- **ZR Express: "coming soon", new platform only** (15 October 2026): ZR is moving its merchants from the old Procolis API to api.zrexpress.app, so a Procolis connector would be thrown away soon. The connector option "ZR Express" exists now and behaves like Manuel (with a notice on the courier form); the real connector will target the new platform once its official docs are available. What was learned about Procolis is kept in docs/COURIER_INTEGRATION.md §5.
- **Courier prices are per account, not public**: Yalidine prices depend on the departure wilaya and the destination commune and can be imported from its fees API; ZR Express rates are negotiated. The wilaya table stays the single place for rates, filled by import (Yalidine) or by hand (ZR).
- **ERPNext manufacturing is left installed and untouched by this app**: nothing in dz_cod depends on it or disables it. Manufacturing (BOMs, work orders, sector templates) is dz_core's job since October 2026.
- **Courier settings live on the Supplier** (custom fields shown when "Is Transporter" is ticked): a courier is a supplier in ERPNext, no new doctype needed.
- **Hourly status sync is off by default** (setting) and uses the normal workflow actions, so webhooks and stock movements behave as if a person clicked.

## COD accounting (20 October 2026, redone from the SCF advice on 21 October 2026)

Source: the advice doc "Daftar: SCF default accounts and compliance advice" (dafter-core DECISIONS.md, "Chart of accounts and default accounts"), Q15 to Q17.

- **Invoiced and paid at Livrée** (`cod/invoicing.py`): the invoice is made from the delivery note with ERPNext's `make_sales_invoice`, dated the delivery and due that day, payment mode "Contre-remboursement" (dz_core's field). It is the legal invoice (Facture DZ: the e-commerce law 18-05 art. 20 asks for one for every online sale), and dz_core's sales reports count it. A Payment Entry then pays it into the courier's account: the buyer paid the courier, who collects as our agent, so the buyer owes nothing and the courier owes us. At Livrée, not at Expédiée: TVA on goods arises at delivery to the buyer, and a parcel sent back was never sold.
- **One account per courier, 4671n "Transporteur X - encaissements à reverser"** (`cod/accounts.py`, under 4671, made at the courier's first delivery and kept on the Supplier). Not 411: the courier is not a customer, and thousands of private buyers would hide one real debtor. ERPNext lets a Payment Entry pay only into a Bank or Cash account, so these are typed Cash; that tag means nothing in the SCF, where they sit in class 4.
- **One Journal Entry per Versement** clears the courier's account: the bank receives the amount transferred; the fees the courier kept go to its supplier account (group "Transporteurs": 40162), where its monthly invoice books them as 6241 Transport sur ventes with the TVA (a courier statement alone does not support a TVA deduction); each parcel's collection is credited to 4671n. An accepted short payment writes the rest of that parcel off to 65882, money collected beyond what the parcel was worth goes to 75882 (gains and losses never netted); a difference not accepted leaves the rest owed in 4671n, as the order stays Livrée. Money for a parcel that matches no paid order (Inconnue, Invalide, Déjà réglée, or delivered before 0.3.0) and a gap between the transfer and the statement go to 4781 "Versements à identifier", to clear every month. Cancelling the Versement cancels the entry: the courier owes the money again.
- **The delivery fee is an item line** (`FRAIS-LIVRAISON`, group "Frais de livraison facturés", income 7088), taxed by the order's template like the goods: a fee re-billed for a third-party courier stays in the TVA base (CTCA art. 15), so 19 % on the régime réel and part of the turnover on IFU. Until 0.3.0 it was a charge row after the TVA lines; a draft saved again moves to the item line.
- **The month close checks the couriers** (`cod/closing.py`, dz_core's report "Clôture du mois" through the hook `dz_closing_checks`): each courier's 4671n must equal what it still owes for the parcels it delivered, and a debit balance on its supplier account means fees kept without an invoice entered.
- **The accounts are settings** (COD Settings, section Comptabilité), made by `prepare` and on migrate, by SCF number: the bank is the company's default (5121), losses 65882, gains 75882, unidentified 4781, the fee 7088. Switch "Facturer à la livraison" off and none of this happens.
- **Still open** (tax office, in writing, the advice doc's section 9): stamp duty when a buyer pays a courier in cash. **For the accountant**: the 4671n accounts.

## Settlement (Versement)

- **One line per parcel, matched by order name or tracking number.** A tracking number is looked up on the Versement's courier first, then on any courier (29 October 2026, review of 27 October, 2.4): two couriers can number parcels alike, and another courier's parcel must still show as Invalide rather than go unnoticed. Yalidine's sync and webhook look a parcel up on their own courier only.
- **Net amount is what matters**: difference = (collected − courier fee) − (expected amount − expected fee).
- **One computation of "already received"** (29 October 2026, review of 27 October, 4.2): `cod/received.py`, used by the form's "Déjà versé" (net), the courier's claim when a Versement is booked (gross) and the month close's check of 4671n (gross). It counts the OK and Écart lines of submitted Versements of the order's own courier, the only ones booked against the order. The three used to differ (net or gross, own courier or any, every line or booked ones): money paid for a parcel before its delivery here (an Invalide line, booked to 4781) made the month close show a false gap of the parcel's amount. A test replays a random sequence of Versements and checks 4671n against the month close after each step.
- **Line statuses**: OK, Écart, Inconnue, Déjà réglée, Invalide. Only OK lines (and Écart lines ticked "Accepter") move the order to Réglée on submit.
- **Only "Livrée" orders can be settled**: an order still "Expédiée" is shown as Invalide; mark it delivered first (the list view allows bulk workflow actions).
- **"Missing" = delivered by this courier up to the settlement date, not in this statement and not paid yet.**
- **Cancelling a Versement puts its orders back to "Livrée" by writing the field directly**: a Workflow cannot move backwards.
- **A dispute stays on the order until a later Versement pays the rest**: an order can be paid over several Versements. "Déjà versé" on a line = the net of the order's lines in earlier submitted Versements of the same courier; the line then expects only the rest, "Charger les commandes livrées" pre-fills only the rest (no fee again), and "Encours transporteurs" shows the rest as owed and as "Montant en litige". Found in the 15 Oct 2026 demo walk: before this, the next Versement pre-filled the whole order again and it was booked as paid twice.
- **A Versement cannot be cancelled while a later Versement settled one of its disputed orders on the rest**: cancel the later one first, or the order would stay Réglée while paid short.
- **Tolerance** (COD Settings, default 0 DA) for rounding differences.

## Webhooks

- **Classic document-event Webhooks with a condition** `doc.workflow_state == "…" and doc.has_value_changed("workflow_state")`: they fire once per move, respect the "Enabled" box and run in the background after the database commit. Frappe v16's "workflow transition" webhooks were rejected because they run synchronously (a down n8n would block the button) and ignore "Enabled".
- **Created disabled with a placeholder URL, never overwritten afterwards**: the client's real n8n URL survives `bench migrate`. Side effect: a fix to the template needs a manual update or a patch on existing sites.
- **In the template write `doc["items"]`**: `doc.items` is the Python dictionary method in Jinja (bug found by the tests).

## Interface

- **Doctype names in English, user-facing labels in French**: code stays English (rule 6), and `translations/fr.csv` shows "Versement", "Paramètres COD", "Commande", etc.
- **Sales Order is relabelled "Commande"** and Delivery Note "Bon de livraison" in French through the same CSV.
- **English and Arabic, by translation, not by rewriting**: the app stays written in French and `translations/en.csv` gives the English version of each text (about 250). Frappe's usual way is the opposite (English source, French translation), but switching would mean renaming every label and changing the workflow state values already stored in clients' orders. With a translation file nothing stored changes: an order stays "Livrée" in the database and is shown as "Delivered" to English users. Each user picks their language (User → Language). `tests/test_translations.py` fails when a new French text has no English line. The welcome guide (plain HTML) holds both versions. "Client" is deliberately not translated: Frappe uses "Client" as an English word too (OAuth Client), and the CSV applies to the whole site. Account names, item names and other data stay as entered. **Arabic** works the same way with `translations/ar.csv` (Modern Standard Arabic; standard ERPNext terms reused where they exist: إشعار التسليم, العميل, الأصناف; "courier" is شركة التوصيل as Algerian shops say it); Frappe mirrors the screen right-to-left by itself. The Arabic file also names our own doctypes and reports, which are English in the code. "Code" is left out of it: Frappe already translates it.
- **Reports use plain SQL**: easier to read for someone who knows Oracle SQL than Frappe's query builder.
- **Reports default to the COD Settings company** when the company filter is empty.
- **A "COD" module sidebar** groups orders, settlements, reports and settings. No desktop icon: the icon grid is being retired in v16.
- **The COD sidebar is mounted on ERPNext's left rail** (`dz_cod/dock/dz_cod/dz_cod.json`, a v16 "Dock" with `mount_on: erpnext`): a truck icon next to Vente/Stock. Without it a normal user had no way to reach the COD menu (it only opened from a direct link). Mounting rather than adding a separate "COD" app tile keeps one app and one rail for the client.
- **A COD home page ("Accueil", the first item of the COD menu)**, built like ERPNext's own module home pages: a standard Workspace (`dz_cod/dz_cod/workspace/cod/`) holding a "life of an order" overview, an onboarding checklist (`module_onboarding/`, `onboarding_step/`), four live counters (`number_card/`: to confirm, to ship, in transit, money held by couriers), two charts (`dashboard_chart/`) and link cards. All standard Frappe records, shipped as files and loaded by `bench migrate`. The overview is a Custom HTML Block, which Frappe cannot ship as a file, so `setup/install.py` creates it from `setup/home_block/` on install and migrate. Onboarding steps tick themselves when the matching record exists (a courier, an item, an order...), so an already-running shop sees most steps done. Each user can fold the overview (**Réduire**) or close it (**✕**); the choice is a per-user default saved on the server (`cod/home.py`), so it follows them on every device, and **Paramètres COD → Réafficher le guide d'accueil** brings it back. An administrator can also remove the block for everyone with the page's standard *Edit* mode.
- **No VAT by default**: ERPNext's setup wizard makes "Algeria TVA 19%" the default sales tax template, which the order form adds to every order typed by hand. Since October 2026 this is dz_core's tax regime, chosen in `prepare`: IFU (the usual case) unticks it, régime réel keeps it. The demo loader uses dz_core's `unset_default_templates` (the demo shop is IFU).
- **No stamp duty on COD parcels by default** (22 October 2026, dz_core 0.4.0 `stamp.py`): whether the "droit de timbre de quittance" is due when the buyer pays the courier in cash is open with the tax office. dz_core's switch can add "Contre-remboursement" only at the seller's charge (445751 and 6457 on the invoice, total unchanged), because the courier collects the order's fixed amount and the Versement must match it.

## Demo data

- **Invented seller "Encre & Fil SARL"**, brands "Encre Urbaine" (printed designs) and "Fil Doux" (basics), couriers "Rapide Express (démo)" and "Colis Sahara (démo)" on the Mock connector. None resembles a real brand.
- **ERPNext's Algerian chart of accounts** ("Algerie - Plan Comptable General 2 avec code") for the demo company, DZD, Africa/Algiers, French interface.
- **30 products, ~260 variants** (size × colour), unit "Pièce", realistic DZD prices and costs.
- **History is replayed day by day through the real workflow**, so the demo data is exactly what the app produces (stock ledger, delivery notes, returns, settlements).
- **Idempotent keys**: orders by "Customer's PO" = `DEMO-0001`…; settlements by reference; everything else by name. A fixed random seed gives the same demo every time.
- **The loader refuses to run on a site holding another company's orders**: protection against loading fake data into a client site.
- **Prices are set by the loader**: ERPNext only applies the price list in the browser form, not on server-side inserts.
- **Disputed parcels stay disputed in the demo** (the next weekly statement does not re-pay them), so the outstanding report has something to show.
- **Wipe = cancel and delete in reverse order, keep the company**; a total reset is simply dropping and re-creating the demo site. Since 0.3.0 a parcel's stock moves span two doctypes (shipment and return transfers, inspections, delivery notes): they are undone together, latest posting first, or cancelling a shipment would leave its delivery note short of stock "Chez transporteur" (22 October 2026).
- **The opening stock enters against the opening account 479** (dz_core's `opening_account`), like a client's opening count: not against the item groups' accounts (7245, 6571...), which would put it in the results and hide a production gap from the monthly close (22 October 2026).

- **Phone checks warn, never block** (16 October 2026, Adem's choice): a refused-parcels warning on the order (threshold in COD Settings, default 1, 0 = off) and a duplicate-phone warning on the customer, both with links. Blocking was rejected: the operator knows the customer. Customer phones are now normalized like order phones, so the comparison works.
- **Return-rate report needs a minimum sample** (16 October 2026): filter *Minimum de colis* (default 5 finished orders); below it the rate is empty and the row sorts last. Products are still counted in pieces; the new column counts orders.
- **Webhook templates: refresh only what nobody edited** (16 October 2026): a fingerprint of the template we wrote is kept in the site defaults; migrate updates template + condition only when the site still has our last version. URL, Enabled and headers are never touched.
- **Our own shipping label with a pure-Python Code 128** (16 October 2026): no new package on the servers; the 106 bar patterns come from python-barcode (MIT) and the test decodes our output back. Code set B only (tracking numbers are plain ASCII).

## Offers: optional features per client

- **À la carte, not tiers** (16 October 2026, Adem's choice): base for everyone, plus a hand-picked list of
  4 optional features per client (`courier_api`, `phone_checks`, `n8n_webhooks`, `labels_reports`).
- **The list lives in site_config.json** (`dz_features`, was `dz_cod_features`): only the vendor, who has the server, can change
  it; clients are never System Manager. Key missing = the base only (20 October 2026; it was "everything", which gave a
  site made by hand or restored without its site_config every option for free); `"all"` = everything, for demo and test sites.
- **Hidden, not greyed out**: reports and print formats are switched off with their own `disabled` field
  (Frappe then removes them from sidebar, workspace and print menu and refuses them by URL), buttons are
  hidden from `frappe.boot.dz_features`. Filtering the sidebar in the boot hook was rejected: Frappe sends
  freshly built sidebars by other paths that would bring the links back.
- **A downgrade never breaks orders**: a courier set to Yalidine works as Manuel when `courier_api` is off;
  the n8n webhooks remember whether they were on and come back as they were.
- **apply_features() runs after every migrate**: migrate re-imports the standard reports and print format,
  which would switch them back on.

## Tests

- **Tests live in `dz_cod/tests/`, outside doctype folders**: this way Frappe does not try to build ERPNext's own test records (slow and fragile); our fixtures reuse the demo setup functions and everything is rolled back after each test class.
- **The courier sync test patches `frappe.db.commit`**: the real job commits after each order, which would otherwise make test data permanent.
